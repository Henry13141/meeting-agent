# 硬件与语音组合建议

建议先用 **SenseVoiceSmall 在 CPU 上转写，加一个自行配置的远程 OpenAI 兼容文本模型**，验证录音、逐字稿、问答和纪要，再根据本机测量决定是否增加专用 VAD/唤醒模型、使用 NVIDIA GPU 或试配 Qwen3-ASR。远程文本模型只处理问答/总结等相关文字，不能代替本地 ASR；它也会收到这些文字，需按自己的会议资料要求选择。

本文是当前源码的选配指南，没有做完整的 CPU、内存、显卡和操作系统测试矩阵。表中的 RAM/VRAM 数字只是安排试配的参考起点，**不是最低配置、可用性承诺或采购依据**；不据此承诺转写速度、准确率、最大会议时长或并发能力。先用现有机器测量，不必为了本指南先买硬件。

## 先区分几项能力

| 组件 | 负责什么 | 当前仓库边界 |
| --- | --- | --- |
| 音频采集与前端分段 | 采集录音，根据活动/停顿提交句段 | 默认已有能量门限和分段逻辑；不是完全没有语音活动检测 |
| ASR | 把音频变成文字 | 默认 SenseVoiceSmall；另有 Qwen3-ASR 的本地适配器，运行时不补下载模型 |
| 专用 VAD + KWS | 识别人声活动，检测配置的唤醒关键词 | 可选 Silero VAD 与 sherpa-onnx KWS；桌面入口需要完整的六文件模型目录 |
| 转写后唤醒 | 从已经得到的文字中识别“会议助手”等唤醒词 | 无专用唤醒模型时仍可使用，但必须等本地转写返回 |
| 文本模型 | 会议问答、总结、选择启用的工具 | 用户配置 OpenAI Chat Completions 兼容服务；启用办公工具时还需支持 tool-calling |
| 角色视频 / TTS | 显示动画 / 合成说话声音 | 本地视频动画已提供；TTS 未接入，视频动画不等于语音合成 |

默认能量门限断句当前以约 900 ms 无语音活动作为端点条件，分段上限约 10 秒；停顿满足条件时可以提前提交，**不是每段必等 10 秒**。从说完到看到答案还要加上断句等待、ASR 排队与推理、文本模型请求和回复时间。这里是按句段处理，不是逐 token 的真流式 ASR。

专用 VAD/唤醒检测过慢时，当前前端会回退到音量断句和转写后唤醒；不应把增加模型理解为必然更快。ASR 队列积压达到保护阈值时会停止采集并报错，已有录音保留，不能靠不断堆积队列来维持长会议。

## 按电脑情况选择试配起点

下表的内存指整机 RAM；Apple Silicon 的统一内存同时供系统及计算使用，不能当成独立显存。显卡型号、驱动、系统、剩余可用内存、其他软件及会议内容都会改变结果。

| 电脑情况与参考档位 | 先试组合 | 测量后再考虑 |
| --- | --- | --- |
| 低内存或较旧电脑，例如约 8 GB RAM 或更低 | SenseVoiceSmall CPU + 远程文本模型，先不加专用唤醒模型；在现有设置中关闭“角色动画”，少开录屏和其他重负载软件 | 先确认能否稳定完成实际会议。若频繁交换内存、排队或过热，减少同机负载；录音可保存不代表转写已能实时跟上，不优先堆更大 ASR/本地 LLM |
| 普通 CPU 电脑，例如约 16 GB RAM | 默认组合，转写线程先保持默认；无独立 GPU 也先试录 | 有明确唤醒需求再试完整 Silero VAD + KWS；依据 CPU 占用、停顿响应和误唤醒比较决定是否保留 |
| Apple Silicon，例如约 16–32 GB 统一内存 | 仍从 SenseVoiceSmall **CPU** + 远程文本模型开始 | 当前设备选择只支持 CPU/CUDA，未接 MPS/MLX。内存较大不等于已使用 Apple GPU；Qwen CPU 仅列为高级候选，先测实际负载 |
| NVIDIA GPU 电脑，例如约 32 GB RAM、8–12 GB 或更高 VRAM 的试验环境 | 先让默认组合稳定，再验证 CUDA-enabled PyTorch 与实际 GPU 可用，比较同一 ASR 的 CPU/CUDA结果 | 可按需求试 Qwen3-ASR-0.6B，再评估 1.7B。以上显存档位不保证任一模型、对齐器或同时运行本地 LLM能放下，必须测峰值与余量 |
| 要求全离线，现有电脑可从约 16–32 GB RAM 级别安排小模型试配 | 本地 ASR + **另行部署**的本地 OpenAI 兼容文本服务；先不启用远程 MCP 工具 | 同时测 ASR 与本地文本模型的 CPU/GPU争用及总内存。资源不足时先保留录音/转写、延后问答；仓库不自动附带或部署本地 LLM |

这些档位可以重叠，例如 Apple Silicon 也可以要求全离线。不要把某台机器上的短样例结果推算成整档机器的验收结果，也不要仅按模型参数量计算实际 RAM/VRAM。

## 默认 SenseVoice CPU 配置

先按 [首次配置指引](../给Codex的首次配置指引.md) 安装 Node、Python、系统 ffmpeg 及依赖，按 [模型说明](../models/meeting-asr/README.md) 准备完整的本地 SenseVoiceSmall 模型。模型至少应有 `model.pt`、`config.yaml`，并保留对应版本的词表等运行文件；仅有两个文件并不能证明模型完整可用。

```sh
pnpm install --frozen-lockfile
uv sync --project services/runtime --frozen
uv sync --project services/meeting-asr --frozen --extra funasr
pnpm run setup:local
pnpm run doctor
```

默认目录是 `models/meeting-asr/SenseVoiceSmall/`。其他本机模型目录用 `pnpm run setup:local --asr-model "本机完整模型目录"` 指定；该参数是替换提示，需填写实际目录。配置会把解析后的本机 Python 和模型路径写入忽略 Git 的 `.local-paths.json`，不应复制其他电脑的路径。

使用本仓库锁文件的版本，不照抄上游文档里的 `pip install -U` 升级命令；例如本仓库当前锁定 FunASR `1.4.12`，与上游未来发布或推荐版本可以不同。

默认 ASR 引擎为 `sensevoice`、设备为 `cpu`、PyTorch 转写线程数为 `4`。需要显式指定时，在启动应用的同一终端设置：

```sh
export MEETING_AGENT_ASR_ENGINE=sensevoice
export MEETING_AGENT_ASR_DEVICE=cpu
export MEETING_AGENT_ASR_THREADS=4
pnpm run dev
```

PowerShell 使用 `$env:MEETING_AGENT_ASR_DEVICE="cpu"` 这样的赋值方式。线程数当前允许 1–32，但更多线程不保证更快；改变后需重启应用、用相同材料比较整机负载，避免挤占录音与其他会议软件的资源。

问答与纪要模型在 `.env.local` 中配置以下三个键，值由使用者自己的服务决定：

```dotenv
MEETING_AGENT_API_BASE=https://your-provider.example/v1
MEETING_AGENT_API_KEY=your-key
MEETING_AGENT_MODEL=your-model-id
```

`API_BASE` 是基础地址，应用追加 `/chat/completions`。支持 HTTPS；HTTP 仅允许 `localhost`、`127.0.0.1`、`::1`。本地无鉴权文本服务可留空 key。需要办公工具时，另验证该模型的 tool-calling 和实际工具调用流程，不能只看“已配置”状态。

ASR/VAD 选配解决听音和断句，不等于模型记忆。当前问答会带入近期会议发言及对应会话的历史，历史增长可能增加延迟；逐字稿保存完整，不代表每次请求都会把全文全部发送给模型。本版使用自己的模型调用循环，没有自动上下文压缩；不能承诺换一个更大的模型就永远不忘。选择文本模型时也要测试同一会议的连续追问、前后指代和较长会话的响应时间。

`.env.local` **只接受以上三个模型变量**，不能把 ASR 的 engine、device、threads 或唤醒路径写进去；这些 ASR 变量通过进程环境传入。修改配置后重启应用再测。

## 可选：Silero VAD + sherpa-onnx 唤醒

只有需要更明确的活动检测和专用关键词检测时再增加此组合。官方能力说明见 [Silero VAD](https://github.com/snakers4/silero-vad) 和 [sherpa-onnx KWS](https://k2-fsa.github.io/sherpa/onnx/kws/index.html)；上游特性不能直接当成本应用已经验证的性能。

在本机 ASR 环境中保留 `funasr` 并安装 `voice` extra。`uv sync` 应同时列出需要的 extras；只写 `--extra voice` 可能移除当前环境中不再被选中的 ASR 依赖：

```sh
uv sync --project services/meeting-asr --frozen --extra funasr --extra voice
```

另行准备相互匹配、许可明确的完整模型文件，仓库和上述依赖安装不会替你下载这些权重：

```text
models/meeting-asr/wake/
  silero_vad.onnx
  tokens.txt
  encoder.onnx
  decoder.onnx
  joiner.onnx
  keywords.txt
```

`keywords.txt` 必须按所选 KWS 模型的 token/关键词格式配置，不能只把中文短句当成任意模型都支持的文件格式。当前桌面以“会议助手”作为检测标签；要验证实际说出这个词时能触发，并测常见近音词与背景声音的误唤醒。

在项目根目录启动的 shell 中可设置：

```sh
export MEETING_AGENT_ASR_WAKE_MODEL_DIR="$PWD/models/meeting-asr/wake"
pnpm run dev
```

传入路径需为本机绝对路径；`$PWD` 由当前 shell 解析，不写进 `.env.local` 或本机 JSON 作为待展开的表达式。当前桌面入口把 VAD 和 KWS 作为这套完整目录接入，不提供“只放一个 `silero_vad.onnx` 就启用桌面专用 VAD”的配置。文件缺失时不会报告专用唤醒可用；文件存在也需启动和实际语音验证。KWS 当前使用 CPU，不随 ASR 的 `cuda:0` 一起自动迁移。

## 高级候选：CUDA 与 Qwen3-ASR

源码已包含本地 Qwen3-ASR 适配器，上游提供 [0.6B 模型](https://huggingface.co/Qwen/Qwen3-ASR-0.6B) 和 [1.7B 模型](https://huggingface.co/Qwen/Qwen3-ASR-1.7B)，见 [官方项目](https://github.com/QwenLM/Qwen3-ASR)。两种规模是高级试配候选，**没有在本仓库做不同电脑的硬件矩阵实测**，不能据此承诺比 SenseVoice 更快、更准或更省内存。

建议由技术人员手动试配，不把默认首配流程直接套在 Qwen 上：

1. 安装与该机器匹配的 ASR 依赖及 `qwen` extra，准备完整本地模型。确认 CUDA-enabled PyTorch 与驱动、显卡实际可用；Qwen CUDA 路径还要核对显卡支持 BF16，可让 Codex 用选定的 ASR Python 检查 `torch.cuda.is_available()` 和 `torch.cuda.is_bf16_supported()`，不能只按显存容量选择老显卡。没有 NVIDIA CUDA 时本仓库可以走 CPU，但不提供 MPS/MLX 路径。
2. 手动核对 `.local-paths.json` 中的 `asrPython` 和 `asrModelPath`，分别指向具备该引擎依赖的 Python 和 Qwen 本地模型目录；保留原有正确的 `runtimePython`。它们必须是本机实际路径，不提交。
3. 从同一启动环境设置 `MEETING_AGENT_ASR_ENGINE=qwen`；GPU试配时设 `MEETING_AGENT_ASR_DEVICE=cuda:0`，CPU试配设 `cpu`。显式 CUDA 不可用会报错；`auto` 只在 CUDA 与 CPU 间选择，不会选择 Apple GPU。
4. 重启应用，做独立启动、短音频和正常会议验证。需要时间片段时另准备匹配的本地强制对齐模型，通过 `MEETING_AGENT_ASR_ALIGNER_MODEL_PATH` 指定；对齐器也占资源，不默认加入首轮比较。

**当前配置陷阱：** `setup:local` 检查的是 SenseVoice 的 `model.pt/config.yaml`，`doctor` 也按这两个文件及 `funasr` 模块检查，不是一键 Qwen 配置或验收工具。有效 Qwen 目录可能被报模型文件缺失，纯 Qwen 环境可能被报缺少 FunASR；应识别这一脚本限制，不能把它写成“Qwen 首配已通过”。也不能只改 `MEETING_AGENT_ASR_MODEL_PATH`：Main 会用 `.local-paths.json` 的 `asrModelPath` 覆盖它，可能仍拿旧的 SenseVoice 目录启动 Qwen。

当前 Qwen 适配在 CPU 使用 FP32、CUDA 使用 BF16，未接入自动量化、vLLM 或 MLX 后端；设备不支持所用精度时需先排查兼容性。Qwen 不支持本适配器中的说话人分离。桌面托管当前也固定关闭 diarization，不能因为 ASR 服务命令行另有 CAM++ 参数，就声称桌面已经自动区分参会者。

## 全离线需要另做什么

提前安装全部依赖、准备完整本地 ASR/KWS/对齐模型，再断网验证。ASR 服务运行时强制离线，缺文件不会运行时补下载。文本问答要另外部署能提供兼容接口的本地文本模型，应用不负责自动下载、部署或挑选它；仅配置 ASR 不会自动获得离线问答。

将模型 API 指向自己的 loopback 服务；启用工具时选支持 tool-calling 的本地模型并实测。全离线使用不要启用依赖远程办公 API 的 MCP server，也不要把远程文本服务配置保留成“离线模型”。不配置文本模型时仍可录音、转写和回看，但问答/自动总结会提示未配置。

云端 ASR、远程语音合成尚未接入，不能作为“低配电脑一键转云端”的现成组合。角色视频本地播放，与这些服务是否可用无关。

## 用自己的会议测量后再升级

先保留一份默认组合的记录，再一次只改一个因素，例如设备 CPU→CUDA、ASR 模型或是否启用专用唤醒。用同一套音频、相同会议场景和文本模型服务比较，记录系统、CPU/GPU、总内存、可用内存、引擎、线程、模型版本与实际配置；不要把本机凭据和不必要的会议原文放进公开结果。

1. **本机短样例。** 使用本人同意测试、人工核对过文字的短音频，测冷启动、首次转写和预热后的转写时间；观察人名、术语、停顿处切分及唤醒。可用 [ASR 冒烟与基准入口](../services/meeting-asr/README.md)。当前 `meeting_asr.benchmark` 每条音频限 20 秒；它输出样本哈希、转写时间、RTF和可选 CER，没有参考文本时不能得出准确率。它测模型回放，不能代替麦克风与界面端到端测试。
2. **一场正常长度会议。** 按实际会议时长运行，同时开启平时用的视频会议、浏览器等软件。记录停止说话到逐字稿出现的延迟分布、CPU负载、进程与整机内存、交换内存、ASR队列是否持续积压、热降频和录音可回放情况。GPU机器另看显存峰值及其他进程占用；基准的PyTorch分配峰值不等于整机总显存峰值。
3. **连续问答与总结。** 在持续录音时连续提问并生成纪要，分别记录“断句/ASR返回”“文本模型开始请求/回复”“界面展示”的时间，避免把网络或模型服务慢误判为 ASR 慢。纯本地文本模型要特别看它与ASR争用CPU、内存或GPU后的排队变化。
4. **再决定是否升级。** 如果瓶颈是模型接口延迟，先处理接口/文本模型；如果是活动检测或唤醒误触发，比较完整VAD/KWS与默认回退；如果ASR本身持续跟不上，再比较CUDA或其他已适配模型。以整场会议的稳定性和文字质量决定，保留有负载增长余量的组合，不用单次最快结果替代验收。
